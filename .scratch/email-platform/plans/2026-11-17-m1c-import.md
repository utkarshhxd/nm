# M1c — CSV import Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** An operator uploads a CSV, confirms a column mapping, and the file becomes contacts — with every count broken out and every rejected row explained.

**Architecture:** Upload to a temp path, sniff the first 100 rows for a mapping proposal, then `COPY` the whole file into a per-import staging table and run one set-based upsert out of it. Rust touches each row exactly once, on the way into `COPY`, because three things cannot be done in SQL: `users::normalize_email`, the UUIDv7 contact id, and the erasure HMAC. Everything after that is set-based, which is the only shape that meets the budget.

**Tech Stack:** Rust (axum, sqlx 0.9, `copy_in_raw`), Postgres 16, React + TypeScript.

**Spec:** `.scratch/email-platform/specs/2026-11-12-m1b-segments-and-import.md` §7 (pipeline, staging, de-duplication, the guard, what an import may and may not do), §12 (API), §13 (UI). Budget from `spec.md`: **Import, 1M-row CSV — < 2 min**.

**Scope:** The CSV import pipeline and its wizard. `POST /contacts:batchUpsert` appears in the same §12 block but is **not** in this milestone — it is the JSON bulk API, it has no mapping step, and `spec.md:107` puts only "CSV import with field mapping, de-duplication and validation" in M1. Say so in the milestone record rather than letting it look forgotten.

## The four decisions this plan makes that the spec left open

Each one is a trap with a silent failure mode. They are here, once, because every task below depends on them.

**1. The erasure guard cannot be `contacts::create`.** `src/contacts/mod.rs:174` states the rule: *"Every write path into `contacts` must go through this function or re-check `suppressions::is_erased` itself."* A set-based upsert is exactly the bulk `INSERT` that sentence warns about. But `is_erased` calls `lock_address`, which takes `pg_advisory_xact_lock` **per address** — a million of those is not a pipeline, it is an outage.

So the importer **re-checks, set-based**: it computes `crypto::suppression_hmac(secrets, &normalised)` per row during `COPY` (it is already touching each row) into a staging column, and the upsert anti-joins `suppressions` on `reason = 'gdpr_erasure'` and `(workspace_id = $1 or workspace_id is null)`. No advisory locks.

The residual race — an erasure committing between the anti-join and the import's `COMMIT` — is closed as far as a statement can close it: the **last statement before `COMMIT`** re-runs the anti-join against the rows this import inserted, deletes any that now match, and counts them in `failed`. What remains is the microseconds between that statement and the commit. **File it as an issue; do not leave it implied.** A guard whose hole is written down is a guard; one whose hole is assumed is a surprise.

**2. Contact ids must be UUIDv7, and Postgres 16 has no `uuidv7()`.** `contacts::create` says why: *"a selection's snapshot is `id <= as_of`, so a contact id that is not time-ordered escapes that bound entirely."* `gen_random_uuid()` in the upsert would compile, pass every test that does not use a selection, and quietly break segment snapshots for every imported contact. Ids are generated **in Rust**, during `COPY`, with `Uuid::now_v7()`.

**3. The importer must undo exactly what the exporter did.** `src/contacts/export.rs:81` is the contract, written for this milestone: strip one leading `'`, and in `lists`, `tags` and every multi_select `attr:<key>`, split on a `;` that no backslash precedes, then turn `\\`, `\;` and `\:` back into `\`, `;` and `:`. For `lists` only, split each entry at its one unescaped `:` into name and status. **One unescape function, used everywhere** — the exporter has one escaper, and two unescapers would drift.

**4. A blank cell is not a null.** In *update existing* mode a blank leaves the existing value alone. Clearing a field through import needs an explicit sentinel, and the mapping UI says so. Getting this backwards wipes data the operator never meant to touch, and the import reports success.

## Review Focus

Five input classes the spec implies and no task's happy path exercises. Each one's test is listed in the task that owns the code.

1. **A CSV whose header names a custom field that was deleted between sniff and start.** The mapping proposal is stale. Expect a `422` naming the column, not a panic and not a silent drop of that column. (Task 9)
2. **A file that is not UTF-8, or that contains a lone `\r`.** Expect a refusal naming the row, not mojibake stored as a contact's name. (Task 4)
3. **An address that normalises to one already in the file.** Last-wins inside the file, counted — and the count must be reported separately from `skipped`, or an operator cannot tell a collapse from a dedup. (Task 5)
4. **A column mapped to a `number` custom field whose cell is `-5-5` or `1e999`.** The exporter deliberately leaves those prefixed as text. Expect a per-row `import_errors` entry, not a `500` and not a silent `NULL`. (Task 4)
5. **An import started while another is running in the same workspace.** Expect `409 import-in-progress` naming the running import, from the advisory lock and not from a status read — two requests must not both pass the check. (Task 8)

### Task 5: One set-based upsert, three de-duplication modes, and the erasure anti-join

**Files:**
- Modify: `src/contacts/import/staging.rs`
- Test: `tests/import.rs`

**Interfaces:**
- Consumes: Task 4's staging table.
- Produces: `pub async fn upsert_from_staging(tx: &mut PgTransaction, import: &ImportJob) -> ApiResult<UpsertCounts>` returning `imported`, `updated`, `skipped`, `collapsed`, `failed`.

One `insert … select … on conflict (workspace_id, email)` per mode:

- **update existing** (default) — `do update` sets each mapped column with `coalesce(nullif(excluded.col, ''), contacts.col)`, which is decision 4 in SQL: a blank cell leaves the existing value alone.
- **skip existing** — `do nothing`, matched rows counted in `skipped`.
- **fail on duplicate** — a pre-flight `exists` join; any match aborts **before any write**, status `failed`, reason naming the first colliding address.

Duplicates inside the file are resolved last-wins by `row_number desc` in the select, and counted in `collapsed` — separately from `skipped`, because an operator cannot otherwise tell a within-file collapse from a dedup against existing data.

The erasure anti-join is decision 1: `where not exists (select 1 from suppressions where reason = 'gdpr_erasure' and email_hmac = s.email_hmac and (workspace_id = $1 or workspace_id is null))`. The matched rows are counted in `failed` with reason `address-erased`, echoing nothing beyond the address the operator supplied.

### Task 6: What an import may and may not do to memberships

**Files:**
- Modify: `src/contacts/import/staging.rs`
- Test: `tests/import.rs`

**Interfaces:**
- Consumes: Task 1's `MembershipSource::Import`, `lists::MembershipStatus`, Task 3's `ImportJob`.

The tables are **`list_memberships`** (`migrations/0012_lists.sql:25`) and **`contact_tags`** (`migrations/0013_tags.sql:16`). Note the trap: `memberships` (`migrations/0005_workspaces.sql:5`) is a different table entirely — it is which *users* belong to a workspace. Writing to it instead would compile and would be a tenancy incident.

An import **may** create contacts, update their fields, add tags, and subscribe them to a list. It **may not** resurrect an unsubscribed membership: a row whose address is already `unsubscribed` on the target list stays unsubscribed. §7.5 names the reason, and it is the M1a bulk-subscribe lesson — unsubscribing removes a row, it does not un-send.

**That row is counted in `memberships_declined`, not in `skipped`** — see Task 1. The contact itself is still imported or updated, so counting it as a skipped row would both double-count it and break Task 7's sum.

A suppressed address **may** be imported — suppression is about mailing, not existence — and does not become mailable. The summary says how many imported contacts are suppressed.

Every membership this task writes carries `source = 'import'`.

## Gates, in the mandatory order

`cargo test`, `cargo clippy --all-targets -- -D warnings`, `cargo fmt --check`, `cargo sqlx prepare --check`, `scripts/check-spdx.sh`, `pnpm -C web typecheck`, `pnpm -C web build`, `pnpm -C web check:bundle`, `pnpm -C web e2e`. **Report every exit code.**

Build order is `pnpm -C web build`, then `cargo build --release --bin nm`, then e2e. `cargo build --release` is a no-op after a web-only change, because rust-embed bakes `web/dist` in at compile time. Delete the binary **inside the container** — `target` is a docker volume, so a host-side delete deletes nothing — and grep the rebuilt binary for a string you just added. Never pipe a build to `/dev/null`: a swallowed `tsc` failure leaves a stale `dist` and the next run looks like a result.
