# Glossary

The domain vocabulary of NM. Use these terms, not synonyms, in code, issues and tests. The M1a entries are taken from §3 of `.scratch/email-platform/specs/2026-11-11-m1a-contact-core.md`; the M1b entries from §3, §4, §7 and §8 of `.scratch/email-platform/specs/2026-11-12-m1b-segments.md`.

**Contact** — a person in one workspace, identified by email address. Has built-in `first_name` and `last_name`, a timezone, and values for the workspace's custom fields. A contact belongs to exactly one workspace; the same address in two workspaces is two unrelated contacts.

**Custom field** — a typed, workspace-scoped definition. Values live in the contact's `attributes` JSONB, keyed by the field's immutable `key`.

**List** — a named set of contacts a campaign can be sent to. Has its own double-opt-in setting and a visibility that decides whether it appears in the preference center (M1c).

**List membership** — the relationship between a contact and a list, carrying the subscription status. This is where "unsubscribed from this list" lives.

**Unsubscribe (a list member)** — sets a membership to `unsubscribed` and keeps the row: that someone opted out of this list is the fact worth keeping, and a later import must not re-add them as new. Route `POST /lists/{list_id}/members/{contact_id}/unsubscribe`; handler `unsubscribe_list_member`; and from the contact's side `POST /contacts/{id}/lists/{list_id}/unsubscribe`, handler `unsubscribe_contact_from_list`; `lists::unsubscribe_member`; audit action `list.member_unsubscribed` (`LIST_MEMBER_UNSUBSCRIBED`). These names superseded `DELETE /lists/{id}/members/{contact_id}`, `DELETE /contacts/{id}/lists/{list_id}`, `remove_list_member`, `remove_contact_from_list`, `remove_member` and the audit action `list.member_removed` (`LIST_MEMBER_REMOVED`) in M1b (issue `08`, 2026-11-13). Nothing is removed, so nothing is called `remove`.

**`list.member_removed`** — the audit action the system wrote for the same operation until M1b. Superseded by `list.member_unsubscribed`, but **never rewritten**: rows already in `audit_log` keep it, so the log still says what the system called the operation at the time. Anything that reads audit actions must accept both, and read them as the same operation.

**Tag** — a label on a contact. Unlike a list, a tag is never a send target and carries no subscription state. Tags organise; lists receive mail.

**Suppression** — a standing block on an address or a domain. Workspace-scoped or instance-wide. This is the only thing in the system that can say "never email this, whatever else says otherwise".

**Eligible** (or *mailable*) — a derived property, never stored: a contact is eligible for a list when their membership is `subscribed` and no live suppression matches their address or its domain.

**Segment** — a named, saved predicate over the contacts of one workspace. It stores rules and never a membership list, so the answer is worked out afresh every time it is asked. A segment is not a list: a list is something a person joins, whose membership carries a status and a consent record, while a segment is a question asked of the data. Nothing is added to a segment and "remove from segment" is not an operation. Table `segments`, code in `src/segments/`.

**Rule** — one leaf test inside a segment: a field from the whitelist, an operator typed by that field's kind, and a bound value. Rules sit in groups, each group matching `all` or `any` of its children; a group nests at most three deep, holds at most twenty direct children, and a whole document holds at most fifty leaf rules. An empty group would match every contact in the workspace, so it is refused when the document is parsed rather than compiled into SQL. The AST and parser are `src/segments/rules.rs`; `src/segments/compile.rs` turns a parsed document into parameterised SQL and binds every value.

**Selection snapshot** — what is written down when someone selects contacts to act on. `POST /contacts/selection` evaluates the predicate once and inserts the contact ids it matched into `selection_snapshot_members`, under a parent `selection_snapshots` row holding the size, the predicate as it was sent, and an `expires_at` one hour out. The token handed back names the snapshot and nothing else — `{workspace_id, snapshot_id, issued}` — so no predicate travels with it and no caller can describe a wider set than the one that was frozen. A snapshot ends when the same actor makes a new selection, when the sweep reaches it, when its hour is up, or when a crash truncates the `unlogged` members table, and all four produce the same `422 selection-expired` rather than an empty page. See `docs/adr/0004-selection-is-a-materialised-set.md`.

**Frozen set** — the contact ids a selection snapshot holds, as opposed to the live filter the grid draws, which keeps moving. A bulk action **narrows `contacts` by** the frozen set and never reads ids out of it: narrowed, a contact deleted since the selection is simply absent and the affected count is short, whereas supplying the ids would hit a foreign-key violation that kills the whole action. Because identity is recorded rather than inferred, nothing anyone else writes can widen the set or swap one contact for another, and a contact that has changed so that it no longer matches **is still acted on** — the person confirmed *these contacts*, not *this query*.

**Provenance** — how a list membership came to exist, recorded in `list_memberships.source` and named `MembershipSource` in `src/lists/mod.rs`. Three values are written today: `ui` for a single add by a signed-in user, `api` for one by a workspace key, and `bulk` for `bulk/subscribe`. The column's check constraint also permits `import` and `form`, which nothing writes until M1c and M1d. It is nullable with no default, so NULL means "written before provenance was recorded" rather than a backfilled guess, and it is replaced when an unsubscribed membership is revived, because the live row answers "how did *this* membership arise" and not "what happened to this person" — that history is M1d's consent log. A cookie session reads as `ui`, so a script reusing a cookie cannot be told from the web UI; only an API key reliably means `api`. Note that **`source` is overloaded and `provenance` is not**: the segment work uses "source" for where a rule's field resolves from in SQL (spec §4.2's table), which is a different idea entirely, so use *provenance* for the membership sense and never for the other.
